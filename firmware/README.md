# BinSight Device Firmware

The ESP32 sketch is in `esp32/device/device.ino`. Open that sketch folder in Arduino IDE, select your ESP32 board and port, and install the `PubSubClient` library from Library Manager. Device-specific settings live in the ignored `esp32/device/secrets.h`; `esp32/device/secrets.example.h` is the safe template.

Before flashing, fill in `SSID`, `PASSWORD`, `MQTT_USERNAME`, `MQTT_PASSWORD`, `MQTT_HOST`, and `DEVICE_ID` in `secrets.h`. `DEVICE_ID` must match the registered bin's `bin_id` in MongoDB. Use the same broker username/password as `backend/.env`, but never commit `secrets.h`. Each board gets its own config copy with its own registered bin ID; the shared `.ino` can stay the same. For a device on the same LAN, set `MQTT_BIND_ADDRESS` to the server's LAN interface address and set `MQTT_HOST` to that same address. For an off-site device, use a VPN interface address and port 1884.

The sketch publishes sensor telemetry at startup and every two minutes to `binsight/devices/{DEVICE_ID}/telemetry`. While connected, it also publishes a retained MQTT status heartbeat every two seconds with an offline last will; the backend marks it offline after five seconds without a heartbeat. It retries Wi-Fi and MQTT connections, republishes a fresh sample after reconnect, and retains the latest uniquely identified telemetry sample so the backend can recover it after a restart. It sends `fill_level` (0-100 percent), `gas_level` (calculated MQ-135 PPM, capped at 100000), and `flame` (boolean). If the ultrasonic sensor misses an echo, it still publishes the gas/fire readings and a heartbeat; the backend retains the last valid fill reading. Verify fill calibration and the flame threshold in Serial Monitor. MQTT setup and the broker start command are in `../backend/MQTT_SETUP.md`.

Check electrical levels before connecting sensors. ESP32 GPIO is not 5 V tolerant. An HC-SR04 Echo output is commonly 5 V and needs a suitable voltage divider or level shifter. Powering an MQ-135 module at 3.3 V does not guarantee its analog output cannot exceed the ESP32 ADC limit; measure the output and add conditioning as needed. MQ-135 sensors also need warm-up and deployment-specific calibration.
## Using a device outside the laptop's network

The ESP32 sends a reading every 120 seconds while connected. Its data path is MQTT broker → FastAPI subscriber → MongoDB; retained latest-sample delivery recovers the newest reading if FastAPI restarts. Historical samples missed while the ESP32 itself is powered off cannot be reconstructed. The ESP32 does not need to be plugged into the laptop, but it does need Wi-Fi and a broker hostname/IP it can reach from its location.

For a device on a different network, do not use `localhost` or a private LAN address that the device cannot route to. This firmware and FastAPI subscriber currently support plain MQTT only; run both on the same reachable private network, preferably through a VPN. Set `MQTT_BIND_ADDRESS` in the server's `backend/.env` to its LAN/VPN interface address and use that address for the device's `MQTT_HOST`. Do not bind plain MQTT port 1884 to a public interface. The Compose API is loopback-bound by default; put it behind HTTPS for remote app access, set `APP_BASE_URL` to the HTTPS API URL, and set `CORS_ORIGINS` to the exact Flutter web origin. A TLS-only managed broker needs TLS support added to both clients before this firmware can use it.
Register each bin in the app first, then copy its exact MongoDB `bin_id` into that device's `DEVICE_ID`. On the server, verify FastAPI logs that MQTT is connected. The device Serial Monitor should show Wi-Fi/MQTT connection and a successful publish. After the next sample, `GET /devices` should show the new `last_updated`, fill, air, fire, and critical status. Fill alerts use 70% by default. Air is the MQ-135 PPM estimate calculated by the firmware and stored in `gas_level`. The calculation depends on `r0`, load resistance, and the module calibration; calibrate these for the actual sensor. The default Poor-air alert boundary is 501 PPM.
